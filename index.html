一个项目，三种来源，

03
代码上下文

工程目录的只读上下文快照；原始模块仍由各自 Git 仓库维护。

02 / Current product

同步只是底层能力。
上层是项目记忆。

FileShare 不要求团队学习提交、分支和合并。它把需要判断的变化显性化，把机械的版本管理留在后台。

01

多项目工作区

每个项目独立绑定 GitHub 仓库和三类本地目录；左侧栏快速切换，不混用同步状态与历史记录。

02

自动同步与冲突保护

文件变化自动形成版本并同步。发现冲突就暂停并保留双方内容，不会为了“同步成功”静默覆盖。

03

可读的项目动态

规则引擎把一次文件更新整理成业务变化、工程影响与风险提示；固定规则运行时不消耗 AI Token。

04

云端文件与版本浏览

在桌面端直接查看 GitHub 当前文件、目录和历史版本，明确区分本地工作副本与云端生效版本。

05

README + AGENTS.md

项目说明与机器协作规约跟随仓库同步，形成团队成员和不同 Agent 都能复用的项目入口。

03 / Share with an Agent

分享一个项目，不再先写安装手册。

每个项目都能生成一段专属提示词。把它交给同事正在使用的 Agent，Agent 会下载官方版本并绑定准确仓库；登录、授权与本地目录仍由成员本人确认。

  1. 固定官方域名、版本文件与 SHA-256 校验流程。
  2. 绑定当前项目仓库，不复用分享者的本地路径。
  3. 逐项询问共享文件、知识库和代码上下文目录。
  4. 遇到登录、授权、覆盖或合并风险时停下来交给人。

04 / Clear boundaries

项目可以统一，
边界必须清楚。

FileShare 把安全行为做成默认规则，而不是藏在设置深处。需要人判断的地方会停下来，不替用户做不可逆决定。

✓
文件在团队自己的 GitHub

桌面端直接连接已授权仓库；FileShare 不要求把项目文件先上传到另一套云存储。

✓
凭据进入 macOS 钥匙串

GitHub 授权信息使用系统安全存储；项目分享提示词不包含密码、Token、本地路径或文件内容。

✓
代码上下文不替代工程仓库

统一仓库保存可查询的项目快照；工程团队仍在原始模块仓库提交代码，不制造双向 Git 冲突。

✓
敏感证据默认隐藏

活动记录可以提示风险与类别，但不会在界面中直接展示凭据、身份材料和其他严格敏感内容。

05 / FAQ

开始之前，先把工作方式说清楚。

01团队成员需要会 Git 吗？

不需要。成员只需连接 GitHub 仓库、选择三类目录并开启自动同步。提交、拉取和安全版本由 FileShare 在后台处理。

02为什么必须选择三类目录？

这是 FileShare 的项目规约：共享文件对应日常业务材料，知识库对应 Obsidian 等长期知识，代码上下文对应工程快照。三者用途和生命周期不同，不应该被迫整理成同一种本地结构。

03分享项目时会暴露我的本地路径吗？

不会。分享提示词只包含官方下载安装流程、当前 GitHub 仓库和安全步骤。新成员需要在自己的电脑上重新选择三个目录。

04代码会不会和原模块仓库冲突？

不会直接写回原模块仓库。代码上下文作为项目级快照进入统一仓库，工程提交仍回到各模块自己的 Git 工作流。

05当前支持哪些平台？

当前正式发布 Apple 芯片 Mac 版本，安装包经过 Developer ID 签名和 Apple 公证。其他平台会在完成同等级别的安装与同步验收后发布。
